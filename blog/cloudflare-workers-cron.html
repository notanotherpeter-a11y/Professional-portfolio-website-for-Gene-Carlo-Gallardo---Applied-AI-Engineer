Cloudflare Workers as Your Cron Job: Ditching GitHub Actions for Scheduled Tasks

August 2026 · 3 min read · Gene Carlo Gallardo

Last week a client's LinkedIn post went out twice. Same content, posted two minutes apart, at 9 AM AEST. The comment section noticed. It wasn't a great look.

The root cause was a classic race condition: two independent schedulers both reading from the same Supabase table before either one had marked the post as published. Both found the same row, both published it, both marked it done — but the damage was already done.

How It Happened

The LinkedIn scheduling system had been built with GitHub Actions as the scheduler — a schedule: trigger firing at 0 23 * * * (9 AM AEST). At some point, a Cloudflare Worker was also given a cron for the same time slot.

GitHub Actions runners queue behind other jobs in the runner pool. They can be delayed by seconds or even minutes. On this day, they both happened to fire within the same execution window, before either had committed the "posted" status back to the database.

The read-before-write gap is where race conditions live. If two processes both read the same row as "pending" before either writes "posted", you get double execution.

The Fix

The solution was simple: make Cloudflare Workers the single source of truth for all scheduling, and remove GitHub Actions schedules entirely.

In wrangler.toml:

[triggers]
crons = ["0 23 * * *", "0 2 * * *"]
# 0 23 * * * = 9 AM AEST (UTC+10)
# 0 2  * * * = 12 PM AEST (UTC+10)

In .github/workflows/publish.yml:

on:
  workflow_dispatch:  # Manual trigger only — scheduling via CF Worker cron

GitHub Actions is still there for manual deploys and testing. But it no longer has any scheduled triggers.

Why CF Workers Cron Is Strictly Better

This isn't a knock on GitHub Actions — it's excellent for CI/CD. But for scheduled API tasks, CF Workers has structural advantages:

  • No runner queue. GitHub Actions scheduled jobs queue behind other runners in the pool. Under load, your 9 AM job might run at 9:04 or 9:11. CF Worker cron fires directly in their infrastructure — millisecond-level precision.
  • No cold start penalty for your code. Workers use V8 isolates, not containers. Startup is microseconds, not seconds.
  • Direct API access. The Worker already has your secrets (LinkedIn token, Supabase URL). No environment variable pipeline to manage in a YAML file.
  • One system to reason about. When something goes wrong, you check the Worker logs. Not the Actions logs, not the runner logs, not the secret sync between both.
  • Free tier covers most scheduling use cases. 100,000 requests/day, cron included.

The Remaining Risk

Consolidating to a single scheduler eliminates the race condition between two systems. But if your Worker itself gets invoked twice simultaneously (unlikely but not impossible in edge cases), you still need database-level protection.

The real fix for that is an atomic update — instead of:

// 1. SELECT where status = 'pending'
// 2. POST to LinkedIn
// 3. UPDATE status = 'posted'  ← gap lives here

Use a conditional update:

// UPDATE posts SET status = 'posted'
// WHERE id = $id AND status = 'pending'
// RETURNING id
// → only proceeds if this process "won" the update

If the update returns no rows, another process already claimed it. Skip the API call. This makes the operation idempotent regardless of how many times it fires.

Takeaway

For scheduled tasks that call external APIs: use Cloudflare Workers cron, not GitHub Actions schedule. Use your database as the lock. And always verify your scheduler count before shipping — two is one too many.
